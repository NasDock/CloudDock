## CLOSE_WAIT / fd 泄漏排查与修复

背景：server（Fastify + ws，端口 3300）出现大量 CLOSE_WAIT，fd 泄漏 + CPU 空转。

排查结论：
- 数据库侧无问题（Prisma 单例 SQLite、ioredis lazyConnect + retryStrategy:null）。
- 主要问题在 WS 会话清理和 nas-client 转发本地服务的 HTTP 请求。

已修复：
1. `server/src/gateway/connection-pool.ts` — 心跳判定死亡时只 removeConnection 从不关 socket，改为 `ws.terminate()`；removeConnection 增加兜底 terminate。
2. `server/src/gateway/ws-heartbeat.ts` — 超时时用 `ws.close(1006)`（1006 是保留码不能发送，关闭失效），改为 `ws.terminate()`。
3. `nas-client/src/client.ts` forwardHttpToLocal — 剥离 connection/keep-alive 等逐跳头、`agent: false`、30s `req.setTimeout` + destroy、补 `res.on('error')`。
4. `nas-client/src/modules/http-proxy.ts` forwardToLocal — 同上处理。
5. `nas-client/src/modules/health-check.ts` — 修复 ws:// 被错转成 https:// 的协议 bug（导致每 30s 对明文 HTTP 做 TLS 握手）；catch 分支原先误判为 healthy；补 drain response body。
6. `nas-client/src/modules/proxy-server.ts` — error 路径补 `socket.destroy()`。
7. `nas-client/src/modules/tcp-relay.ts` — localSocket error 时补 destroy。

备注：工作区未安装 node_modules（npm registry 走 127.0.0.1:7890 代理但代理未开），无法本地跑 tsc 验证，改动均为标准 ws/http API 使用。

## 项目代码熟悉（全库阅读）

通读 SPEC/ARCHITECTURE/VERIFICATION 与 server / nas-client / shared / web / mobile / desktop 核心源码，形成 CloudDock 运行机制认知：

- 三类通道并存：
  1) HTTP 隧道穿透：外网请求 `/{username}/{tunnelName}/*` → server `http-proxy` → `ws-tunnel` 经 `/ws/device` 推给 NAS → NAS `forwardHttpToLocal` 回本地服务；
  2) WebRTC P2P（主用）：`/ws/signal` 信令（nas 用 clientKey、mobile/desktop 用 JWT，按 deviceId 路由）→ P2P DataChannel 走 proxy_connect/data/close 流式 TCP 代理（NAS 端 proxy-server），大文件走 large payload；TUN/VPN 模式已 soft-disable（client.ts startNetworkServices 注释掉）；
  3) 本地转发模块：nas-client 的 tcp-relay / http-proxy / port-forwarder / vpn-gateway。
- 配对：无 clientKey 时走 6 位 pairing code（server pendingPairings），Web UI 批准后签发 `ck_*` 永久 key 落 config。
- DB 用 Prisma + SQLite：User / Client / Tunnel / RequestDevice（访问设备审批）/ DirectTrafficLog（直连流量上报）/ AccessLog / RefreshToken。
- RequestDevice 审批机制：外部设备访问隧道时自动注册，默认 autoApproveNewRequestDevices=true，否则 pending/blocked 拒绝（403）。
- 流量统计：隧道流量来自 AccessLog 聚合（TRAFFIC_QUOTA 按 plan 限配额），WebRTC 直连流量由客户端上报 DirectTrafficLog。
- 关键路径文件：server `app.ts`（preHandler 捕获 /{user}/{tunnel}）、`gateway/*`；nas-client `client.ts`(622行)、`webrtc/webrtc-manager.ts`(469行)、`local-api.ts`(5700 端口)。

## 手机异地组网访问 NAS 失败 — 根因定位 + 修复

现象：WebRTC 组网成功（data channel open），但浏览器访问 100.64.0.1:3000 超时（WiFi / 蜂窝均失败）。

根因（adb logcat 实锤）：
`CloudDockVpn: Error reading from TUN: java.lang.RuntimeException: Cannot convert argument of type class java.util.LinkedHashMap at Arguments.fromJavaArgs ... CloudDockVPNModule.emitEvent ... CloudDockVpnService.handleTcpPacket:229 (vpnProxyConnect)`
RN 事件 emit 不能直接传 Kotlin Map（mapOf() → LinkedHashMap），VpnService 事件桥接炸掉，异常冒泡到 readLoop catch → break，TUN 读循环死亡 → proxy 流量全丢。vpnProxyData/vpnProxyClose 同理全会炸。

修复：`CloudDockVPNModule.kt` eventSink 增加 `toWritable()` 递归转换（Map→WritableMap、List→WritableArray），再 emit。

其他发现（未修，待确认后处理）：
1. `vpn-store.ts` 调用 `addVPNRoutes`，但 `native/vpn.ts` 没有这个导出 → 路由动态更新静默失败（TypeError 被 catch 吞掉）。
2. `CloudDockVpnService.addRoutes()` 是"重启整个 VPN"实现，会清空所有 stream 状态。
3. 手机→NAS 数据用二进制帧，NAS→手机用 JSON+base64，NAS 端 handleBinaryMessage 只认二进制，格式不对称。
4. proxy-server.ts 不把 close/error 映射回 proxy_close/proxy_error 给 peer。
5. Android 手写 TCP 栈无重传/拥塞控制（丢包即死流）。
6. 日志里 SharedSocket connect_error timeout 是走公网隧道 /mmdctjj/ad2 的另一条路径，与组网访问是不同问题。

验证途径：local-api(127.0.0.1:5700)/status 无日志字段；浏览器端难抓日志。建议给 ProxyClient/vpn-store 加日志或 adb logcat 复测。
